# Design

## Context

См. `proposal.md` — Why. Существующее состояние, которое формирует подход:

- Слои сервиса: `routers` → `services` → `schemas`, конфиг через `app/config/`, без БД и без репозиторного слоя.
- `Qwen3-Embedding-0.6B` уже загружается при импорте `app/llm_services/llm_setup.py` (1.1 ГБ, CPU); второй инстанс поднимать нельзя.
- Legacy-путь `/clinrec_checking/check` использует Chroma и захардкоженный retrieval; контракт менять нельзя, но и переиспользовать его нельзя — запросы там протокол-центричные.
- Backend передаёт только presigned GET на PDF (900 с), доступ к S3-креденшелам у ML нет.
- Тестовый документ — `КР62_3.pdf` (артериальная гипертензия, ~325 тыс. символов, ~80 страниц), текстовый слой есть, но таблицы при простом извлечении слипаются.
- Каталога `storage/` в проекте нет; `docker-compose.yml` монтирует модели и Chroma томами.

## Goals / Non-Goals

**Goals:**

- Независимый `POST /check_dms`, не связанный с legacy-путём и Chroma.
- Детерминированная разметка исходного текста: код вставляет границы, модель их не вычисляет.
- Локальное хранилище без отдельного сервиса (`storage/qdrant`).
- Повторное использование уже загруженной модели эмбеддингов.
- Индексация документа один раз на содержимое (по хэшу).

**Non-Goals:**

- OCR сканов и PDF без текстового слоя.
- Хранение каталога «МКБ → клинрек» — это зона backend.
- Оценка дозировок, кратности, лекарственных взаимодействий и противопоказаний по состоянию пациента.
- Асинхронная очередь задач и поллинг статуса.
- Изменение legacy-эндпоинта, Chroma-коллекций и существующих промптов.

## Decisions

### 1. Qdrant в локальном режиме

`QdrantClient(path="storage/qdrant")` — файловая БД в процессе.

Альтернативы: Qdrant-контейнер (лишний сервис в compose, нужен только для одного эндпоинта), Chroma как в legacy (второй стор на той же библиотеке, но хуже фильтры по payload и смешение с legacy-коллекцией), numpy-поиск в памяти (теряется между запросами).

Следствия локального режима, которые нужно учесть в реализации:

- один процесс — `uvicorn` запускать без нескольких воркеров (текущий Dockerfile так и делает);
- файл-лок может конфликтовать при рестарте с `--reload`, поэтому клиент создаётся один раз при старте, как модели;
- upsert выполняется под `asyncio.Lock`, чтобы параллельные запросы не писали одновременно.

### 2. Идентичность документа по `sha256` в payload

Чанк хранит `file_hash`; перед индексацией `count(filter file_hash)`.

Альтернатива — отдельный `index_manifest.json`: дублирует состояние Qdrant и рассинхронизируется при сбое. Отклонено.

`uuid5(file_hash, chunk_index)` делает повторный upsert идемпотентным: дубликаты не появляются, даже если проверка пропущена.

### 3. Контракт ответа — сегменты, а не строка со скобками

Ответ содержит массив `{text, unnecessary}`; склейка текста равна исходной строке.

Альтернативы:

- строка с `[позиция]` — потребителю нужно парсить строку, а во входе могут быть свои `[`, `]`, вложенные и незакрытые скобки;
- offsets — требует арифметики на клиенте и ломается на суррогатных парах UTF-16 (фронт на JS).

Сегменты не требуют парсинга ни на бэке, ни на фронте. Бэк может склеить их в любой формат для UI.

### 4. Разбиение назначений и вердикт — два разных вызова

1. **split** (`GigaChat-3-Pro`): строка → нумерованный список позиций.
2. **verdict** (`GigaChat-3-Ultra`, `with_structured_output(method="function_calling")`): позиции + найденные фрагменты → номера лишних позиций.

Почему не одним вызовом: между шагами нужен retrieval, а он требует отдельных позиций как запросов.

Фолбэк split без LLM: разделители `;`, перевод строки, `•`. Если split не дал результата — позиция считается одна (вся строка), retrieval идёт по ней целиком.

Для каждой роли объявляются отдельные настройки в `GigaChatConfig`; `GigaChat-3-Ultra` использует ultra `base_url`/`scope`, `GigaChat-3-Pro` — стандартный endpoint (если недоступен, переключение на ultra — одна строка в `LLMFactory._create_chat`).

### 5. Модель возвращает индексы, код — границы

Модель никогда не возвращает `start`/`end`: на кириллице она регулярно ошибается в посимвольных смещениях. Схема ответа:

```python
class UnnecessaryItem(BaseModel):
    index: int = Field(ge=1)   # номер позиции из переданного списка
    text: str                  # для сверки с позицией
    reason: str | None = None  # только для логов

class VerdictResult(BaseModel):
    unnecessary: list[UnnecessaryItem]
```

Валидация: `index` в диапазоне, при расхождении `text` и позиции приоритет у `index`, расхождение логируется. Границы сегментов считает код по исходной строке (`str.find` с нормализацией пробелов).

### 6. Парсинг PDF — `pdfplumber`

Даёт координаты и таблицы; простой text layer перемешивает колонки — на тестовом документе таблицы «Показание / УУР / УДД» превращаются в одну строку, из-за чего retrieval по препаратам деградирует.

Чанкинг: разделы по заголовкам вида `3.4.2 …`, окно 800–1200 символов с overlap ~120, отдельный чанк на строку таблицы в текстовом виде `Показание: … | Уровень: …`. Payload: `file_hash`, `section`, `page`, `chunk_index`.

### 7. Индексация и поиск

Эмбеддинги — `clinrec_emb_model` из `llm_setup`, батч 16, `normalize_embeddings=True`, размерность 1024.

Поиск — по каждой позиции отдельно, top-4, фильтр `file_hash`, дедупликация, не более 20 чанков в промпт. Если назначение не найдено ни в одном фрагменте, оно помечается лишним — это требование продукта.

### 8. Хранение PDF и синхронный ответ

`storage/pdfs/{sha256}.pdf` — том в compose. Объём мал (единицы МБ на клинрек), зато переиндексация при смене чанкера не требует S3.

Ответ синхронный, клиентский таймаут 180 с: первый запрос — 20–40 с индексации плюс 5–20 с ultra, повторный — 5–20 с.

### 9. Промпт: лишнее только при отсутствии подтверждения

Вердикт «лишнее» ставится, если позиция не подтверждается документом; «не назначено, но рекомендовано» не добавляется. Промпт требует учитывать МНН, класс препарата и синонимы, чтобы торговое название не помечалось лишним.

## Risks / Trade-offs

- **Ложное «лишнее» по торговому названию** (например, «Кардиомагнол» вместо ацетилсалициловой кислоты) → в промпте требование сопоставлять по МНН/классу/АТХ; фрагменты возвращаются, чтобы врач видел основание; при массовом ложном срабатывании добавляется словарь синонимов.
- **Таблицы PDF** → `pdfplumber`; если структура не восстановилась, строки таблицы всё равно попадают в текст, хуже — только точность.
- **Модель ошиблась в выборе позиции** → текст не портится (границы ставит код), ошибка видна как неверная подсветка; `text` и `index` сверяются.
- **Локальный Qdrant и параллельные записи** → один клиент, `asyncio.Lock`, один процесс uvicorn.
- **Смена модели эмбеддингов или чанкера** → без манифеста старые чанки не отличить от новых; при смене конфигурации каталог `storage/qdrant` очищается вручную. Осознанно принято ради простоты.
- **Нет цитаты для «не упоминается»** → фрагментов по такой позиции нет; это ожидаемо и не является ошибкой.
- **Медицинская ответственность** → эндпоинт выдаёт подсказку, а не заключение; ответ не содержит назначений и рекомендаций к лечению.

## Migration Plan

- Новые зависимости: `qdrant-client`, `pdfplumber`.
- Новые каталоги: `storage/qdrant`, `storage/pdfs`; добавить в `.gitignore`.
- Том в `docker-compose.yml` для `ml-service`: `./storage:/app/storage` (аналогично существующим томам моделей).
- Откат: удалить роутер из `app/routers/__init__.py`, остановить сервис, удалить `storage/`. Legacy-путь не затронут.

## Open Questions

- Максимальный размер PDF (50 МБ) и таймаут скачивания (30 с) — значения по умолчанию, уточняются по реальным файлам.
- Нужен ли порог косинусной близости, ниже которого позиция не считается найденной, — решается после прогона на нескольких клинреках.
