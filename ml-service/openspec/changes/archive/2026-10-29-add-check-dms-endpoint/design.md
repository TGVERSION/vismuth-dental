# Design

## Context

См. `proposal.md` — Why. Существующее состояние, которое формирует подход:

- Слои сервиса: `routers` → `services` → `schemas`, конфиг через `app/config/`, без БД и без репозиторного слоя.
- Локальная `Qwen3-Embedding-0.6B` загружается в `app/llm_services/llm_setup.py` для legacy-пути; на CPU она векторизует клинрек минутами, а GPU на сервере нет. Поэтому для ДМС эмбеддинги берутся из API GigaChat (`EmbeddingsGigaR`, 2560 измерений).
- Legacy-путь `/clinrec_checking/check` использует Chroma и захардкоженный retrieval; контракт не меняется и не переиспользуется.
- Backend — смежная зона: пока он не вызывает эндпоинт, контракт можно зафиксировать без оглядки на presigned-ссылки.
- Тестовый документ — `КР62_3.pdf` (артериальная гипертензия, 3.2 МБ, ~220 страниц, 325 тыс. символов), текстовый слой есть, но таблицы при простом извлечении слипаются.
- Ожидаемый максимальный файл — 30 МБ; каталога `storage/pdfs` нет.

## Goals / Non-Goals

**Goals:**

- Независимый `POST /check_dms` с файлом в теле запроса; S3 и presigned-ссылки в ML не участвуют.
- Файл обрабатывается в памяти, без записи на диск и без последующей уборки.
- Векторизация через GigaChat API: без локальной модели, без GPU и без минут ожидания на CPU.
- Детерминированная разметка исходного текста: границы вставляет код, модель их не вычисляет.
- Локальное хранилище чанков без отдельного сервиса (`storage/qdrant`).
- Индексация документа один раз на содержимое (по `sha256`).

**Non-Goals:**

- OCR сканов и PDF без текстового слоя.
- Хранение каталога «МКБ → клинрек» — это зона backend.
- Оценка дозировок, кратности, лекарственных взаимодействий и противопоказаний по состоянию пациента.
- Асинхронная очередь и фоновая индексация (даже для файлов у верхней границы размера).
- Ограничение параллелизма индексации.
- Изменение legacy-эндпоинта, Chroma-коллекций и существующих промптов.

## Decisions

### 1. Вход — `multipart/form-data`, файл в памяти

Тело запроса: `file` (`UploadFile`), `mkb` и `appointments` (`Form`, строки). Файл читается чанками по 1 МБ в `bytes`, `sha256` считается на лету, превышение 30 МБ обрывает чтение и даёт `413`. Парсинг — `pdfplumber.open(io.BytesIO(content))`.

Альтернативы:

- **presigned URL на S3** — уже был реализован, но требует доступа ML к хранилищу, presign-логики на backend и делает локальную проверку зависимой от MinIO;
- **временный файл в `storage/tmp` с удалением в `finally`** — то же самое плюс риск остатков при жёстком kill процесса;
- **`UploadFile` напрямую в `pdfplumber`** — работает, но `sha256` и проверка сигнатуры требуют содержимого целиком, а два чтения одного потока усложняют код.

Память выбрана как единственный вариант без внешних зависимостей и без уборки. 30 МБ `bytes` на запрос для сервиса с низкой нагрузкой приемлемы.

`UploadFile` у Starlette — `SpooledTemporaryFile`: до 1 МБ в памяти, больше — в системном временном файле, который закрывается и удаляется автоматически. В `storage` ничего не пишется.

### 2. Qdrant в локальном режиме

`QdrantClient(path="storage/qdrant")` — файловая БД в процессе.

Альтернативы: Qdrant-контейнер (лишний сервис), Chroma как в legacy (смешение с legacy-коллекцией и хуже фильтры по payload), numpy-поиск в памяти (теряется между запросами).

Следствия локального режима: один процесс (uvicorn без нескольких воркеров), клиент создаётся один раз при старте, upsert выполняется целиком после всех эмбеддингов.

### 3. Идентичность документа по `sha256` в payload

Чанк хранит `file_hash`; перед индексацией `count(filter file_hash)`.

Альтернатива — отдельный `index_manifest.json`: дублирует состояние Qdrant. Отклонено.

`uuid5(file_hash, chunk_index)` делает повторный upsert идемпотентным. Хэш считается по содержимому файла, поэтому одна и та же рекомендация, загруженная повторно, индексации не требует.

### 4. Контракт ответа — сегменты, а не строка со скобками

Ответ содержит массив `{text, unnecessary}`; склейка текста равна исходной строке назначений.

Альтернативы: строка с `[позиция]` (потребителю нужно парсить строку, а во входе могут быть свои скобки) и offsets (арифметика на клиенте, суррогатные пары UTF-16). Сегменты не требуют парсинга ни на бэке, ни на фронте.

### 5. Разбиение назначений и вердикт — два разных вызова

1. **split** (`GigaChat-3-Pro`): строка → нумерованный список позиций.
2. **verdict** (`GigaChat-3-Ultra`, `with_structured_output(method="function_calling")`): позиции + найденные фрагменты → номера лишних позиций.

Между шагами нужен retrieval, а он требует отдельных позиций. Фолбэк split без LLM: разделители `;`, перевод строки, `•`; при неудаче — одна позиция (вся строка).

`GigaChat-3-Ultra` использует ultra `base_url`/`scope`, `GigaChat-3-Pro` — стандартный endpoint. Если Pro на стандартном endpoint недоступна, переключение — одна строка в `LLMFactory._create_chat`.

### 6. Модель возвращает индексы, код — границы

Модель не возвращает `start`/`end`: на кириллице она ошибается в посимвольных смещениях. Схема ответа — `{index, text, reason?}`; `index` проверяется по диапазону, `text` используется для сверки, при расхождении приоритет у `index`. Границы сегментов считает код по исходной строке.

### 7. Парсинг PDF — `pdfplumber`

Даёт координаты и таблицы; простой text layer перемешивает колонки — на тестовом документе таблицы «Показание / УУР / УДД» превращаются в одну строку, что ухудшает retrieval по препаратам.

Чанкинг: разделы по заголовкам вида `3.4.2 …`, окно 800–1200 символов с overlap ~120, отдельный чанк на строку таблицы в виде `Показание: … | Уровень: …`. Payload: `file_hash`, `section`, `page`, `chunk_index`.

### 8. Индексация и поиск

Эмбеддинги — GigaChat API, модель `EmbeddingsGigaR` (2560 измерений), батч до 64 текстов, клиент один на процесс (SDK сам обновляет токен). Локальная модель для ДМС не используется; Qwen остаётся только в legacy-пути. Поиск — по каждой позиции отдельно, top-4, фильтр `file_hash`, дедупликация, не более 20 чанков в промпт. Позиция, не найденная ни в одном фрагменте, помечается лишней — это требование продукта.

## Risks / Trade-offs

- **Память на запрос** (до 30 МБ `bytes` плюс структуры `pdfplumber`) → при низкой нагрузке приемлемо; ограничение параллелизма сознательно не вводится.
- **Время обработки**: 220 страниц — парсинг ~34 с, 713 чанков — 12 запросов к API (~15 с), итого около минуты. Файл 30 МБ — это ~2000 страниц: парсинг 5+ минут, ~6700 чанков и 2–3 минуты эмбеддингов. Повторный запрос идёт по кэшу хэша.
- **Стоимость токенов** → каждый новый клинрек расходует токены GigaChat на эмбеддинги: ~200 тыс. на типовой файл и ~2 млн на файл в 30 МБ; повторные запросы с тем же файлом бесплатны благодаря кэшу по `sha256`.
- **Сетевая зависимость** → без доступа к GigaChat индексация невозможна; ошибка API отдаётся как `502 embeddings_unavailable`.
- **Ложное «лишнее» по торговому названию** → в промпте требование сопоставлять по МНН/классу/АТХ; фрагменты возвращаются, чтобы врач видел основание.
- **Параллельные upsert в локальный Qdrant** → один клиент, нагрузка низкая; риск принят, семафор не вводится.
- **Смена модели эмбеддингов** меняет размерность (2560) и делает старые чанки несовместимыми: при смене модели `storage/qdrant` очищается и документы индексируются заново.
- **Нет цитаты для «не упоминается»** → фрагментов по такой позиции нет; это ожидаемо.
- **Медицинская ответственность** → эндпоинт выдаёт подсказку, а не заключение; ответ не содержит назначений и рекомендаций к лечению.

## Migration Plan

- Новые зависимости: `qdrant-client`, `pdfplumber`, `python-multipart`, `gigachat`.
- `DmsConfig`: остаются `qdrant_path`, `collection`, `max_pdf_bytes` = 30 МБ, параметры чанкинга и retrieval; `pdf_dir` и `download_timeout` удалены.
- `GigaChatConfig`: `dms_embedding_model` (`EmbeddingsGigaR`) и `dms_embedding_batch` (64).
- Том `./ml-service/storage:/app/storage` остаётся (нужен Qdrant). Каталог `storage/pdfs` не создаётся.
- Backend должен отправлять файл вместо presigned-ссылки — отдельная задача смежной зоны; сейчас эндпоинт никем не вызывается.
- Откат: удалить роутер из `app/routers/__init__.py`, остановить сервис, удалить `storage/qdrant`. Legacy-путь не затронут.

## Open Questions

- Порог косинусной близости, ниже которого позиция не считается найденной, — решается после прогона на нескольких клинреках.
- Ограничения тарифа GigaChat по токенам на эмбеддинги — уточняются по реальному расходу на один клинрек.
